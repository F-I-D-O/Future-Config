# Overview
Future config is a configuration system for software projects and a set of libraries to make this system work in various programming languages.
Currently supported languages are C++, Python and Java.

Future Config can be used as a configuration system for any project but it is designed for complicated projects with dozens of configurable properties. For just a few properties, using program arguments or environment variables may be a better choice.

The main features of Future Config are:

- **Established Config File Format**: Future Config uses [YAML](https://yaml.org/) as the config file format.
- **Default/User Configs**: The configuration is defined in a *default* config file specifying the default values for the project. The user can then create a *user* config file, which is supplied at runtime and overrides the values from the default config file. 
- **Config Class Generation**: Future Config generates config classes representing the config file structure. This allows for reliable and type-safe access to the config properties. The classes are generated automatically, no manual work is needed.
- **Config Hierarchy**: Future Config is designed to support the configuration of whole project dependency chains. This means that a *project B* depending on a *project A* can specify some configuration for *project A* in its own config file. Moreover, the user can then use a single config file for the whole project chain.
- **String Variables**: Future Config supports string variables/placeholders in the config file. This allows for the reuse of values and the composition of more complex values.

Note that Future Config is still not fully implemented. The following table shows the current status of the implementation in different programming languages.

| Feature | C++ | Python | Java |
|---------|-----|--------|------|
| Config File Format | YAML | custom temporary format | custom temporary format |
| Default/User Configs | yes | yes | yes |
| Config Class Generation | yes | yes | yes |
| Config Hierarchy | yes | yes | yes |
| String Variables | yes | yes | yes |
| Documentation | yes | no | no |
| Loading config from program arguments | yes | no | no |

Although the config system should be identical in all supported languages, the necessary integration steps differ. Use the following links to get more information about the integration in a specific language:

## Python

1. `pip install fconfig`
2. Create your master config file in your project's resources
3. Generate config classes:
    ```
	from fconfig import configuration
	configuration.generate_config()
	```
4. Use the generated config classes:
	```
	import yourproject.confi.yourproject_config.config
	```

## C++
The C++ implementation of Future Config requires C++20 support. The library is available as a CMake package.

1. Install the Future Config package:
	- vcpkg: `vcpkg install future-config`
	- cmake:
		1. Install the dependencies: `fkYAML`, `spdlog`, `inja` and `tclap`
		1. Clone the repository
		1. Configure: `cmake <project directory>/cpp`
		1. Build: `cmake --build . --target install`
1. create your master config file
	- by default, the file should be: `<CMakelists.txt directory>/data/config.yaml`.
1. Modify your CMakeLists.txt:
	```cmake
	set(CMAKE_CXX_STANDARD 20) # or higher

	find_package(future-config CONFIG REQUIRED)
	target_link_libraries(your_target PRIVATE future-config::future-config)

	# Run the builder tool that generates the config classes
	setup_fconfig(TARGET_NAMES <target_names>)
	```
	- pass `MAIN_CONFIG_PATHS <paths_to_config_file>` to `setup_fconfig` if your master config file is not in the default location
1. Configure your project using cmake
1. Now, your config classes are generated and ready to use in your project. Basic usage:
	```cpp
	#include <future-config/configuration.h>

	// Include the generated config file
	#include "config/<your_project>_config.h"

	int main() {

		// load the config
		auto config = load<<Your_project>_config>(local_config_path);
	```

# Principles
The Future Config system has a few principles that distinguish it from other config systems. These principles are discussed here. Then, in the [Basic Usage](#basic-usage) and [Advanced Usage](#advanced-usage) sections, we describe how to apply these principles to your project.

The Future Config system has the following key principles:

- **Master config file determines the configuration of the project**: The master config file specifies the configuration parameters of the project, together with the default values. It is the single point of reference for what parameters the project has.
- **Autogenerated config classes**: Instead of dictionaries, dynamic objects or handwritten classes, Future Config generates config classes that are type-safe. Therefore, every automation tool should see the available configuration parameters and their types.
- **Customizable config loading order**: When loading the config at runtime, we can specify multiple sources of the configuration data. These sources are combined automatically based on the specified load order. The order or the number of the sources is not limited, supporting any possible configuration scenario.
- **Hierarchical config, where config sources can bind to any object**: In your program, you can bind a config source to any object in the configuration hierarchy with the root object as the default. This way, config files covering only specific parts of the configuration can be flat, instead of mirroring the entire hierarchy.


## Config load order
The config hierarchy is an ordered list of config definitions. At runtime, Future config reads each config definition into a config object. Then, each the objects are merged together according to the specified load order. If there are the same keys in multiple objects, the key from the object corresponding to the lower level in the config definition hierarchy takes precedence.

There are three types of config definitions:

- the master config definition 
- the user config definition (multiple such definitions are supported)
- the command line config definition

The load ordering is designed for maximum flexibility. Any load order is theoretically possible, inluding loading the same config file multiple times, loading the default config after the user config, etc. However, unless there is a very good reason, we recommend to stick to the default load order, which is:

1. Load the master config files, from the root of the dependency chain to the project itself.
2. Load the user config file
3. Load the config from command line arguments


# Data Types
Each configuration value has a type. The members of the generated config classes have the corresponding types, so no conversion is needed in your program.

| Type | Examples | Not this type |
|------|----------|---------------|
| integer | `42`, `-3`, `0x1F`, `0o17` | `010` (string), `1_000` (string) |
| float | `1.5`, `.5`, `1e5`, `.inf`, `.nan` | |
| boolean | `true`, `True`, `TRUE`, `false`, `False`, `FALSE` | `yes`, `on` (strings) |
| path | `/opt/app`, `./results`, `../data/in.csv`, `~/data`, `C:\data`, `C:/data`, `\\server\share` | `logs/app.log`, `text/plain` (strings) |
| string | anything else, and any quoted value: `"8080"`, `'true'` | |
| array | `[1, 2, 3]` - all items have to be of the same type | |
| object | a map of properties | |

The types of integers, floats, and booleans follow the [YAML 1.2 Core schema](https://yaml.org/spec/1.2.2/#103-core-schema). Null values (`~`, `null`, or a key without a value) and empty arrays are not supported, because they do not determine a type.

A specific type can be forced by a YAML tag:

```yaml
version: !!str 1.5          # string instead of float
log_file: !path logs/app.log  # path instead of string
pattern: !!str ./*.txt      # string instead of path
```

## The master config determines the types
The type of each property is determined by its default value in the master config. The values from the other sources (user config files, command line arguments) are converted to the type of the property:

| Type of the property | Accepted values |
|----------------------|-----------------|
| string | any scalar value, it is used as a text |
| integer | integer |
| float | float, integer |
| boolean | boolean |
| path | path, string |
| array | array, each item is converted to the type of the array items |
| object | object |

Any other value is an error, reported when the configuration is loaded. The error message contains the property, the config source, and both types. Properties that are not present in the master config have the types determined from their values.

For the command line arguments, this means that the value for a string property is always used as it is (`--name 123` is the string `123`), and that the value for a path property does not need the form of a path (`--out_dir results`).

Variables are replaced by the text of the referenced values. The value with resolved variables is then converted to the type of the property. If the default value in the master config contains a variable, the type of the property is determined from the resolved value.

## Paths
Only the values that are unambiguously paths are recognized as paths: the values starting with `/`, `./`, `../`, `~/`, a drive letter (`C:\`, `C:/`), or `\\`. Other values, like `logs/app.log`, are strings unless they are marked with the `!path` tag, or unless they are given for a property that is a path in the master config. Note that the quotes do not prevent the recognition, use the `!!str` tag for a string that looks like a path.

**Relative paths are converted to absolute paths** when the configuration is loaded, so your program does not have to know where the configuration came from:

- a relative path in a config file is relative to the directory of that config file,
- a relative path in a command line argument is relative to the current working directory.

The exceptions are:

- Paths relative to the home directory (`~/...`) are not changed, the `~` is not expanded.
- A path starting with a variable (`${data_dir}/results`) is left to the variable: the variable has to hold an absolute path (a relative path in the variable itself is converted where the variable is defined). If the path is still relative after the variable is resolved, an error is raised.

In the generated C++ config classes, the paths are `std::filesystem::path` members.


# Advanced Usage
Here, the alternative ways of using Future Config are discussed to provide maximum flexibility.

## Command Line
In addition to use a config file, you may also provide configuration via command line arguments. Because these are not hierarchical, you can only use command line arguments for unique keys, otherwise, an exception will be raised.

The translation is as follows:

```yaml
key: value
```

```bash
--key value
```

For boolean values, you may just pass the key without a value, which will be interpreted as `true`.

The values are converted to the types of the properties, see [Data Types](#data-types).

There is one difference between command line arguments and config files: unknown keys are not allowed. The reason for allowing unknown keys in config files is to enable sharing a single config file across different projects. Command line arguments, on the other hand, are principally bound to the specific project and therefore, allowing unknown keys would not make sense.

Only the long arguments (`--key`) are checked. Positional arguments and short options are ignored. If your application processes some long arguments on its own, you can exclude them from the check by listing them as allowed arguments. The `--help` and `--version` arguments are always allowed. In C++:

```cpp
auto config = fc::load<Your_config_class>({
	.command_line_arguments = std::make_pair(argc, argv),
	.allowed_command_line_arguments = {"local_config", "dry_run"} // --local_config and --dry_run are not config keys
});
```

When creating the config definitions manually, pass the allowed arguments as the third argument of the `fc::Command_line_config_definition` constructor.


## Binding config sources to objects
By default, each config source (config file, command line arguments) is bound to the root object of the configuration hierarchy, which means that the config file has to mirror the hierarchy from the root. However, a config source can be bound to any object in the hierarchy. The content of the source is then placed into that object, so a config file covering only a specific part of the configuration can be flat.

The object is determined by a *bind path*: the keys on the way from the root object to the bound object, separated by dots. For example, with the following master config:

```yaml
name: app
server:
  network:
    port: 80
    timeout: 10
```

a local config file bound to `server.network` can be just:

```yaml
timeout: 30
```

The following rules apply:

- The master config files are always bound to the root object.
- Local config files and command line arguments can only be bound to an object that already exists in the configuration, otherwise, an exception is raised.
- Command line arguments are only searched in the bound object. Therefore, a key has to be unique only within the bound object, and the keys outside the bound object are unknown arguments.
- Variables are not affected by binding. They are always specified by the full path from the root object, e.g. `${server.network.port}`, even in a bound config file.

### C++
```cpp
auto config = fc::load<Your_config_class>({
	.local_config_path = "<path_to_user_config_file>",
	.local_config_bind_path = "server.network",
	.command_line_arguments = std::make_pair(argc, argv),
	.command_line_bind_path = "server.network"
});
```

When creating the config definitions manually, pass the bind path as the last argument of the `fc::Config_definition` and `fc::Command_line_config_definition` constructors:

```cpp
config_definitions.emplace_back(std::make_unique<fc::Config_definition>(
	fc::Config_type::LOCAL, "<path_to_user_config_file>", "server.network"
));
```


## Config logging
To find out where the configuration values come from, you can turn on the config logging with the `--fconfig_log <level>` command line argument. The levels are:

- `none`: nothing is logged (default)
- `sources`: the config sources are logged, in the load order
- `values`: the config sources, and all config values with the source they come from
- `chain`: the config sources, and all config values. For each value that was set by more than one source, all these sources are listed, together with the values they provided (overwrite chain).

The sources are numbered in the load order. A source with a higher number has a higher priority, i.e., it overrides the values from the sources with lower numbers. An example of the `chain` level output:

```
Future Config sources (in load order; a source with a higher number has higher priority and overrides the lower ones):
[1] main          /app/data/config.yaml
[2] local         /home/user/network.yaml  -> server.network
[3] command line                           -> server.network
Future Config values ([n] = source the value comes from; in the overwrite chains, the highest number wins):
Configuration
├── name: app                  [1]
└── server
    ├── network
    │   ├── label: app-local   [2]
    │   │   ┆╌╌ [1] default
    │   │   ┆╌╌ [2] ${name}-local
    │   ├── port: 5            [3]
    │   │   ┆╌╌ [1] 80
    │   │   ┆╌╌ [3] 5
    │   └── timeout: 30        [2]
    │       ┆╌╌ [1] 10
    │       ┆╌╌ [2] 30
    └── port: 8080             [1]
```

The solid lines show the configuration hierarchy, the dashed lines show the overwrite chain of a value. For the values that contain variables, the value from the source is shown next to the resolved value.

Notes:

- The `--fconfig_log` argument is processed only if the command line arguments are passed to Future Config. It is never reported as an unknown argument.
- The log is written using the default logger of the [spdlog](https://github.com/gabime/spdlog) library, with the `info` level. Therefore, it is not visible if your application sets a higher log level.
- The `values` and `chain` levels log **all** configuration values, including passwords and other secrets.

### C++
The level can be also set in the code. If the `--fconfig_log` argument is present, it has a priority.

```cpp
auto config = fc::load<Your_config_class>({
	.command_line_arguments = std::make_pair(argc, argv),
	.config_log_level = fc::Config_log_level::SOURCES
});
```

When loading the config from manually created config definitions, pass the level as the second argument of the `fc::load_config` function.


## Customizing the config loading order

### C++
First, we create a list of config definitions:
```cpp
std::vector<std::unique_ptr<fc::Config_definition_base>> config_definitions;
```

Then, we can add the config definitions as we please. Note that the order matters, the last added config definition has the highest precedence.
```cpp
// add the master config definition
config_definitions.emplace_back(std::make_unique<fc::Config_definition>(fc::Config_type::MAIN, "<path_to_main_config_file>"));

// add the user config definition
config_definitions.emplace_back(std::make_unique<fc::Config_definition>(fc::Config_type::LOCAL, "<path_to_user_config_file>"));

// add the command line config definition
config_definitions.emplace_back(std::make_unique<fc::Command_line_config_definition>(argc, argv));
```

Then, we can load the config using the `load` function:
```cpp
auto config = load<Your_config_class>(config_definitions);
```

The default type for the `Config_definition` constructor is `MAIN`, and the default path is `<CMakeLists.txt directory>/data/config.yaml`. Therefore, if we want to use the default master config file, we can create it as:
```cpp
config_definitions.emplace_back(std::make_unique<fc::Config_definition>());
```

# Legacy Principles

- Config propagation to config instances of the dependencies is handled automatically by the builder. The data transfer is a part of the generated code.
- There is only one config instance per project. Dependency config instance in the main/child project is the same as in the dependency project.
- dependency configs need to be specified in a form of key value pairs, where:
	- key is the name (key) of the in the master config file of the main project
	- value is the specification of the dependency config

### Configuring the WSL environment
A working WSL environment is required to run the PowerShell-executed tests (smoke tests, usage tests, vcpkg tests). Additionally, the WSL environment needs GCC 11 as some of the tests use this compiler to test the library on an older compiler.

To install GCC 11 on Fedora, you can use the `install_gcc-11-mamba.sh` script located in the `test` directory. This script uses `mamba` to install GCC 11 into a separate environment, so that it does not interfere with the default system compiler.
